첨부한 ZIP의 LLMNav 소스코드를 검토하고, 실제 사용에 도움이 되는 개선을 구현해줘.
단순한 코드 스타일 정리보다 잘못된 결과, 데이터 손실, 멈춤, 성능 저하를 일으키는 문제를 우선해줘.

1. 프로젝트와 전달본

- LLMNav는 코딩 에이전트가 저장소를 탐색하도록 돕는 Node.js CLI 및 ESM 라이브러리다.
- 소스 주석의 llmnav/1 카드를 읽어 검색 인덱스, 그래프, 컨텍스트와 MCP 도구를 제공한다.
- 전달 기준은 버전 0.13.5, 소스 커밋 2014617이다. 전체 커밋 ID와 파일별 SHA-256은 ZIP 루트의 SOURCE_SNAPSHOT.json에 있다.
- 실제 프로젝트는 ZIP의 llmnav/ 폴더에 있다. 이 프롬프트와 스냅샷 설명은 ZIP 루트에 있다.
- .git, node_modules, 생성 캐시, 실행 중 상태와 임시 파일은 제외했다. 테스트, 스크립트, 문서, 예제, 벤치마크와 탐색 설정은 포함했다.
- .llmnav/ids.jsonl, order.lock, lexicon.json은 ID 수명과 순서, 별칭을 유지하는 자료다. 캐시로 간주해 삭제하거나 새로 초기화하지 마라.
- 현재 실제 HTTP API 클라이언트나 DB 드라이버는 없다. 주요 I/O 경계는 파일시스템과 MCP stdio다. 예제의 effect=db.write 같은 주석을 실제 DB 호출로 오해하지 마라.

2. 시작 방법

먼저 AGENTS.md, README.md, package.json, docs/architecture.md와 관련 소스·테스트를 읽어라.
캐시를 제외했으므로 최초 query/show 실행에 필요한 인덱스를 먼저 생성해야 한다.
Node.js 22 이상에서 llmnav/ 폴더를 작업 디렉터리로 사용해 다음 명령을 실행하라.

  node ./bin/llmnav.js generate --root . --full
  node ./bin/llmnav.js query "검토할 작업의 설명" --top 5
  node ./bin/llmnav.js show <semantic-id>

외부 npm 패키지를 내려받는 npx 호출 대신 포함된 bin/llmnav.js를 사용할 수 있다.
런타임 의존성은 0개이며 현재 작업을 위해 새 라이브러리, DB, 서버를 설치할 필요가 없다.
검증 명령이 없던 .git 정보 때문에 실패하면 Git 메타데이터 부재와 제품 결함을 구분해 보고하라.

3. 최근 수정 사항: 새 증거가 있는 문제를 찾아라

최근 변경은 다음을 다뤘다. 각 변경의 경계와 남은 위험을 확인하되, 이미 해결된 현상을 그대로 다시 보고하지 마라.

- 외부 시간·난수·I/O를 주입할 수 있는 선택적 인자와 AbortSignal 전달.
- MCP 요청과 공유 세션 로딩의 개별 시간 제한, 취소, single-flight, 늦은 결과의 게시 방지.
- 쓰기·close·정리 동시 실패의 원인 보존, AggregateError의 제한된 직렬화, JSON 파싱 cause 보존.
- runRead의 기본 15초 제한과 기본 재시도 0회, 명시적으로 켠 읽기에만 제한된 백오프와 jitter 적용.
- Windows 파일 공유 오류 처리, 락 소유권 변경 직렬화, 생성 트랜잭션 복구와 롤백.
- 포맷 작업의 락 보호와 교체 직전 내용 충돌 검사.
- import마다 만들던 모듈 Set 제거 및 Go import 대상의 사전 분류.
- 리다이렉트의 반복문·Map 탐색, 분기 간 공유 노드의 중복 탐색 방지, 전체 순환 도달 여부의 일괄 검증.
- 생성 파일 검증의 중복 읽기 제거와 제한된 병렬 읽기. 설치 후 검증은 새로 읽는다.
- Go 메타데이터 조회의 동시 실행 수 제한과 공통 조상 디렉터리의 중복 방문 제거.

원본 커밋은 로컬 Windows에서 npm run check의 286개 테스트와 npm pack --dry-run을 통과했다.
이는 전달 당시의 기록이다. 네 수정 후 검증 결과는 네가 실제 실행한 결과로 따로 작성하라.

4. 우선 검토할 문제

아래 항목은 검토 관점이다. 전부 문제라고 가정하거나 억지로 결함 수를 채우지 마라.

A. 결과 정확성과 입력 경계
- 파서가 언어별 문자열·주석·정규식·escape·Unicode·EOF를 잘못 구분하는가?
- 바이트/문자/줄 오프셋, 임계치 직전·정확히 일치·직후, 빈 입력, 중복 ID, 누락·오염된 JSON을 올바르게 처리하는가?
- 포맷이 알 수 없는 메타데이터나 사용자 소스를 손실시키는가?
- 검색과 그래프의 점수, 동점 정렬, 중복 제거, 모호한 ID 및 replacement 후보 순서가 유지되는가?
- 공개 런타임 API와 TypeScript 선언, CLI/MCP 오류 응답 사이에 차이가 있는가?

B. 상태·동시성·파일 안전성
- 공유 스냅샷이나 호출자가 준 객체를 수정하거나 오래된 비동기 결과를 게시하는가?
- 여러 프로세스가 락을 획득·회수·해제할 때 소유권을 잘못 판단하는가?
- Windows/POSIX의 rename, hard link, 경로, 줄바꿈 차이에서 데이터가 손실되는가?
- 실패·취소·프로세스 중단 시 저널과 백업을 이용해 이전 상태나 완료된 상태로 복구되는가?
- 경로 이탈과 symlink/junction 검사를 최적화 과정에서 약화시키지 않았는가?
- 파일시스템 교체가 비협조적인 외부 편집기까지 포함한 원자적 CAS를 제공한다고 잘못 가정하는가?

C. 자원과 장애 격리
- 타이머, 파일 핸들, 스트림 리스너, 락이 실패 경로에서도 해제되는가?
- 기다리기만 중단한 작업이 백그라운드에서 계속 실행되며 자원을 쌓는가?
- 원래 오류와 취소 이유가 fallback, 정리 오류 또는 응답 직렬화에서 사라지는가?
- 공유 작업 취소가 다른 요청에 영향을 주거나 시간 초과 뒤 새로운 작업의 결과를 덮는가?
- 읽기 재시도가 전체 시간·횟수·동시 실행 한도를 지키는가? 쓰기 전체를 재실행하는 경로가 있는가?

D. 데이터 증가에 따른 CPU·메모리·I/O
- 루프 안의 find/filter/includes/indexOf, 반복 Set/Map 구성, 정렬·복사·직렬화가 같은 데이터를 다시 훑는가?
- 긴 리다이렉트, 순환, 재합류 분기, 큰 그래프와 큰 파일에서 실행량이나 메모리가 급증하는가?
- 파일 수 제한만으로 충분한가? 파일 바이트 수와 동시에 유지하는 원본 문자열·파싱 객체·생성물도 고려하라.
- 반복 읽기, 중복 메타데이터 조회, 긴 락 점유, 요청별 제한의 합산 부하를 줄일 수 있는가?
- 캐시 키·수명·무효화가 정확하며, mutable 입력에 대한 캐시가 오래된 결과를 반환하지 않는가?
- 필요한 출력 자체가 큰 경우와 불필요한 중복 계산을 구분하라.
- async 함수와 timeout만으로 동기 CPU 작업이 중단된다고 가정하지 마라.

5. 구현 원칙

- 기존 필수 인자·반환값과 llmnav/1, 생성 인덱스, CLI/MCP의 공개 계약을 유지하라.
- 새 테스트 seam이나 제어 인자는 선택적 options로 추가하고, 생략 시 동작을 분명히 하라.
- 정렬·중복·첫 번째/마지막 항목 선택·오류 우선순위를 먼저 확인한 뒤 자료구조를 바꿔라.
- 변경은 확인된 원인을 소유한 계층에 모아라. 호출부마다 임시 조건을 덧붙이지 마라.
- 무제한 Promise.all로 순차 I/O를 치환하지 마라. 기존 동시 실행 헬퍼와 트랜잭션 단계 경계를 활용하라.
- 쓰기는 응답 유실이나 부분 적용이 가능하다. 전체 작업 재시도로 복구를 대신하지 마라.
- 캐시 무효화나 보안 검사를 삭제해 성능 수치를 개선하지 마라.
- 런타임 의존성 0개와 운영체제 간 결정적 출력을 유지하라.
- 근거가 있는 버그 수정과 직접 관련된 리팩토링에 집중하라. 근거 없는 전면 재작성, 기능 추가, CI 확장과 의존성 도입은 피하라.
- 실제 API·DB가 없는 곳에 가상의 결제·주문 시스템이나 회로 차단기를 추가하지 마라.

6. 검증과 산출물

먼저 영향이 큰 문제를 최대 5개로 우선순위화하고, 각 항목에 다음을 작성하라.
위치(파일·함수), 재현 조건, 기대 결과와 실제 결과, 영향, 근거, 수정 방향.
확인된 결함·정적 위험·미확인 가설을 구분하라. 확인되지 않은 플랫폼 결과나 성능 개선율을 꾸며내지 마라.

실행 가능한 환경이면 우선순위가 높은 문제부터 작은 수정 단위로 구현하고 회귀 테스트를 추가하라.
실행할 수 없으면 그 제약을 명시하고 코드 근거와 적용 가능한 unified diff를 제공하라.

테스트는 변경된 동작과 경계를 검증해야 한다. 구현 모양만 확인하는 테스트나 불필요한 대규모 테스트를 늘리지 마라.
기존 결과의 회귀 여부와 호출 수·방문 수·최대 동시 실행 수를 확인하고, 실행 시간·메모리 수치는 측정 조건과 함께 제시하라.

수정 후에는 관련 테스트를 먼저 실행하고, 최종 상태에서 다음을 확인하라.

  node ./bin/llmnav.js format --root .
  node ./bin/llmnav.js check --root .
  node ./bin/llmnav.js generate --root . --full
  node ./bin/llmnav.js audit --root .
  npm run check
  npm pack --dry-run

생성 캐시는 명령으로 재생성하고 직접 편집하지 마라. 실패한 검증을 통과시키기 위해 기대값이나 안전 검사를 약화시키지 마라.
네트워크 설치, 원격 push, PR 생성, 릴리스와 배포는 수행하지 마라.

최종 답변은 한국어로 다음을 제공하라.
1) 실제로 수정한 문제와 효과.
2) 변경 파일 또는 패치. 파일 첨부가 가능하면 변경된 소스 ZIP도 제공.
3) 실행한 검증 명령과 결과, 실행하지 못한 검증.
4) 남은 위험과 후속 작업 중 영향이 큰 항목만.

결함이나 수정 근거를 찾지 못했다면 그대로 말하라. 변경량을 늘리는 것보다 정확한 판단과 검증 가능한 개선을 우선해줘.
